# Lab notebook: 170Tune qualification and serving rollback

Date: 2026-09-13 UTC

## Scope

This run evaluated the conservative `match`-style SM point and a moderate HBM profile from
[cachenetics/170tune](https://github.com/cachenetics/170tune) on both CMP 170HX cards. Hardware
identifiers are intentionally omitted. Qualification was performed per card while SGLang was
stopped.

The installed 170Tune revision was `93d0e72`.

## Stock snapshot

Both cards passed `preflight` and received independent stock snapshots before any writes:

```text
SM offset: 0 MHz
HBM NDIV: 64
REFRESH: 6
```

The BAR0 helpers were available, the FBPA privilege masks were open, and the driver-reported
memory-clock source was stock.

## HBM qualification

The exact combined profile was tested independently on both cards:

```bash
sudo 170tune -i <gpu> hbm-gate \
  --ndiv 70 \
  --timings "REFRESH 24" \
  --sweeps 12
```

| card | full-VRAM sweeps | memory errors | compute checks | peak HBM |
|---|---:|---:|---:|---:|
| A | 12/12 | 0 | passed | 60 C |
| B | 12/12 | 0 | passed | 60 C |

The resulting HBM profile receipts were stored per card. This is the HBM profile retained for
production.

## SM qualification and the important failure

The candidate SM point was:

```bash
sudo 170tune -i <gpu> gate 250 1400 4
```

Both cards passed four full-VRAM pattern sweeps and the bit-exact dense compute check:

| card | sweeps | compute-check GEMMs | bad elements | peak HBM |
|---|---:|---:|---:|---:|
| A | 4/4 | 59,640 | 0 | 57 C |
| B | 4/4 | 59,776 | 0 | 54 C |

The cards' cooling prevented the default 60 C SM soak target from being reached. More
importantly, the synthetic gate was not sufficient: after SGLang started successfully and one
complete `quick_bench.py` run passed, a later monitored run faulted on card B during the third
1,024-token generation. The server reported `cudaErrorIllegalInstruction`; the kernel reported
Xid 13 (SM warp illegal instruction) followed by Xid 43, and the TP rank terminated.

The `+250/1400` point was therefore quarantined on the failing card. Persistence was disabled
immediately and SM settings on both cards were reset to stock. A synthetic gate receipt must not
be treated as application qualification.

## Serving observations before rollback

The first complete tuned run produced:

| run | decode | TTFT |
|---:|---:|---:|
| 1 | 68.7 tok/s | 0.53 s |
| 2 | 69.1 tok/s | 0.53 s |
| 3 | 69.6 tok/s | 0.54 s |
| median | **69.1 tok/s** | - |

This was 1.8% above the earlier 67.9 tok/s result, but it is not a controlled stock-SM A/B and
must not be presented as a safe gain. During the later monitored run, the two completed samples
were 69.3 and 68.2 tok/s before the fault. Observed maxima across that run were:

| card | utilization | power | core | HBM | effective SM clock |
|---|---:|---:|---:|---:|---:|
| A | 100% | 99.0 W | 38 C | 52 C | 1,470 MHz |
| B | 93% | 97.4 W | 36 C | 49 C | 1,470 MHz |

The low temperature did not prevent the SM fault. This was not a thermal-limit event.

## Final production profile

Only the independently qualified HBM profile is persisted:

```text
SM offset: stock (0 MHz)
SM clock lock: none
HBM NDIV: 70
HBM timing: REFRESH 24
HBM_FORCED: 0
```

Each card has its own persisted profile. `170tune-persist.service` is enabled and applies all
present per-card profiles after the NVIDIA driver is ready. The rejected SM point is not present
in either production profile.

Inspect the live and persisted state with:

```bash
sudo 170tune -i <gpu> status
sudo 170tune -i <gpu> persist status
```

Safe boot rollback:

```bash
sudo 170tune -i <gpu> persist disable
sudo systemctl mask 170tune-persist.service
```

After disabling or masking the service, rebooting leaves the cards at stock. Do not copy a gate
receipt or a persisted profile between cards; qualification is per serial.

## Post-rollback production validation

SGLang was restarted with stock SM settings and the qualified HBM-only profile. The standard
warm-up completed, including decode concurrency 1/2/3 and the prefix-cache request. A fresh
`quick_bench.py` run completed all three 1,024-token samples:

| run | decode | TTFT |
|---:|---:|---:|
| 1 | 70.5 tok/s | 0.57 s |
| 2 | 71.1 tok/s | 0.53 s |
| 3 | 69.4 tok/s | 0.52 s |
| median | **70.5 tok/s** | - |

After the run:

- SGLang health: HTTP 200
- OpenWebUI health: HTTP 200
- OpenWebUI container to SGLang `/v1/models`: HTTP 200, expected served model ID
- live SM offset: 0 MHz on both cards
- live HBM source: userspace NDIV 70 on both cards
- new Xid events since rollback: 0

This is a production sanity result, not a controlled stock-HBM versus tuned-HBM A/B. It proves
that the selected final profile completed the tested serving workload; it does not isolate the
HBM profile's performance contribution.

## Operational conclusion

The production choice is `SM stock + HBM NDIV70/REFRESH24`. The HBM profile survived 24 total
full-VRAM sweeps plus compute checks. The SM profile is rejected despite passing its synthetic
gate because the real SGLang kernel mix found a failure that the gate did not. This is exactly why
the application workload is the final qualification rung.
